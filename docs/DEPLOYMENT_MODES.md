# Deployment modes

`frp-auto-deploy` supports two server deployment modes. Direct mode is the
default and matches 2.0.0. Enterprise single-443 is optional. Project version
**2.1.1** is the current stable release.

Published service ports stay **TCP/6000-6098** (1:1) in both modes.

The addresses `203.0.113.10` and `192.0.2.50` are documentation-only (RFC 5737).

## Why single-443 exists

Some enterprise networks allow TCP to a non-standard port but reset TLS
ClientHello there (DPI / TLS inspection limited to TCP/443). Observed symptom:

```text
# Transport-only diagnostic. This is NOT a trust-validating test.
nc -vz server 6099          # TCP connect succeeds
# The following may be used only to observe the reset; it does not pin the CA:
# curl -vk https://server:6099/ca.crt
# Connected … TLS ClientHello sent … Connection reset by peer
```

Do **not** use `curl -k` / `curl -vk` as a production verification flow.

The same allocator on TCP/443 from an unrestricted Internet host completes
TLS 1.3. Server tcpdump may show the client RST arriving before any TLS
payload, so the handshake never reaches the allocator.

**Do not** “fix” this by serving the allocator over plain HTTP, disabling
certificate verification, moving TLS to another arbitrary non-standard port,
or using `curl -k` in production. Use Enterprise single-443 mode so public TLS
stays on TCP/443.

Direct mode remains valid for hosts that are not behind that class of filter.

## Direct mode (default)

```text
Internet
   |
   +-- TCP/443  --> frps control (native FRP TLS, token auth)
   +-- TCP/6099 --> allocator HTTPS (project CA)
   +-- TCP/6000-6098 --> published services
```

Non-interactive:

```bash
FRP_PUBLIC_HOST=203.0.113.10 \
FRP_DEPLOYMENT_MODE=direct \
sudo bash install-server.sh
```

Public inbound: TCP/443, TCP/6099, TCP/6000-6098. TCP/22 is optional for
server administration.

## Enterprise single-443 mode

```text
Internet
   |
   TCP/443  HTTPS / WSS frontend (nginx, project CA)
        /                          \
       /                            \
allocator HTTPS                  FRP control over WSS
127.0.0.1:6099                   path /~!frp
                                 |
                                 v
                           frps backend
                           127.0.0.1:7000
                           proxyBindAddr 0.0.0.0
                                 |
                          TCP/6000-6098 services
```

Public inbound: **TCP/443** (allocator HTTPS + FRP control over WSS) and
**TCP/6000-6098** (published services). The allocator backend (default 6099)
and FRP control backend (default 7000) must not be published.

Non-interactive:

```bash
FRP_PUBLIC_HOST=203.0.113.10 \
FRP_DEPLOYMENT_MODE=single443 \
sudo bash install-server.sh
```

The official bootstrap URL is unchanged:

```bash
curl -fsSL \
https://raw.githubusercontent.com/datarelay-labs/frp-auto-deploy/v2.1.1/dist/bootstrap-server.sh \
| sudo bash
```

On a TTY the installer offers:

1. Direct
2. Enterprise single-443

Client install commands generated by `frp-create-client` already use
`allocator_public_url` (for example `https://203.0.113.10/enroll`). Enrollment
returns `frp_transport=wss` so the client writes `transport.protocol = "wss"`
and pins `transport.tls.trustedCaFile` to the stored allocator CA. Operators
do not type WebSocket paths or backend ports.

## Frontend choice

Compared for this project: nginx, HAProxy, Caddy.

| Criterion | nginx | HAProxy | Caddy |
| --- | --- | --- | --- |
| Distro packages (Ubuntu/Debian/RHEL/AL2 extras) | Yes | Yes (HAProxy 1.5 on AL2 is old) | Unreliable |
| Isolated config + dedicated systemd unit | Yes | Yes | Yes |
| Long-lived WebSocket timeouts | `proxy_read_timeout` | `timeout tunnel` | Yes |
| Private CA (no automatic public ACME) | Explicit | Explicit | Fights the model |
| Path `/~!frp` (FRP 0.70.1 constant) | Exact `location` | ACL path | Yes |

**nginx** is used because it is present as `nginx` on the supported package
managers, WebSocket reverse-proxy behaviour is stable, and a **dedicated**
unit with `/etc/frp-auto-deploy/frontend.conf` does not take over distro
nginx sites. Direct mode does not install or enable this unit.

The frontend is not the distro `nginx.service`. Uninstall removes
`frp-frontend.service` and does not purge the nginx package.

If the installer added the nginx package, it stops and disables distro
`nginx.service` so the package manager autostart does not bind TCP/80.
A pre-existing active or enabled `nginx.service` is a conflict: single-443
fails before changing a working Direct deployment. A pre-existing inactive
and disabled `nginx.service` is left that way. Reinstall of an existing
single-443 tree is idempotent and does not treat `frp-frontend.service` as
the distro unit. Uninstall never enables or starts distro `nginx.service`.

## TLS termination (single-443)

- Clients open TLS to public TCP/443 (looks like HTTPS).
- nginx presents the existing project `server.crt` / `server.key` under the
  existing private CA.
- `/ca.crt`, `/healthz`, `/enroll`, and `/bootstrap/redeem` are an nginx
  allowlist proxied to `https://127.0.0.1:<allocator_listen>` with
  `proxy_ssl_verify on`, the project CA, and `proxy_ssl_name localhost`.
  nginx `proxy_ssl_verify` does not reliably match iPAddress SANs, so the
  loopback backend is verified as `DNS:localhost` (present on every project
  leaf). The public certificate identity for clients is unchanged. Other
  paths return 404.
- `GET /~!frp` is the FRP 0.70.1 WebSocket path (`FrpWebsocketPath`), matched
  with an exact `location =`. After HTTP Upgrade, nginx proxies to
  `http://127.0.0.1:<frp_control_listen>`. Management POST `/enroll` never
  reaches frps.
- frps backend has `transport.tls.force = false` because the connection from
  nginx is already-decrypted HTTP Upgrade. The backend listens on 127.0.0.1
  only. FRP token authentication is unchanged.
- frpc uses `transport.protocol = "wss"` plus `transport.tls.trustedCaFile`
  pointing at `/etc/frp-auto-deploy/allocator-ca.crt` (same pin as allocator
  HTTPS). There is no fallback to `websocket` without TLS.

First enrollment still:

1. GET `/ca.crt` (no `--cacert` yet; the stored CA file does not exist)
2. verify `FRP_ALLOCATOR_CA_SHA256` against the canonical DER of the **CA**
3. store `allocator-ca.crt`
4. subsequent allocator HTTPS uses `curl --cacert` with that stored CA

Frontend and allocator leaves are both issued by that CA. The fingerprint is
not the leaf. This is not TOFU.

## FRP 0.70.1 facts used (not guessed)

From tagged v0.70.1 source and `conf/frp{c,s}_full_example.toml`:

- `transport.protocol`: `tcp`, `kcp`, `quic`, `websocket`, `wss`
- WebSocket path is **not** configurable; it is `/~!frp`
- Default `transport.tls.enable = true` and `disableCustomTLSFirstByte = true`
- `transport.tls.trustedCaFile` is the documented custom-CA key
- `bindAddr`, `bindPort`, `proxyBindAddr` exist on the server
- `transport.tls.force` rejects non-TLS on `HandleListener`; plaintext WS
  from nginx therefore requires `force = false` on the localhost backend
- Token auth is independent of the transport

FRP is **not** upgraded to 0.71.0 for this mode.

## Migration (Direct → single-443)

This is a **maintenance-window cutover**, not zero-downtime.

Preserved: FRP token, private CA, registry.json, schema v2, client records,
management identities, reserved ports, enrollment files that are still valid.
The installer does not reset the registry.

Existing clients speak native FRP TLS on TCP/443. After cutover they must
speak WSS to nginx on TCP/443. A 2.0.0 client that ignores `frp_transport`
will enroll/apply HMAC-OK and then fail to connect until the client software
is 2.1.0+ and Apply rewrites `frpc.toml`.

A pre-2.1 `config.json` that omits `deployment_mode` is treated as Direct.
Re-running with `FRP_DEPLOYMENT_MODE=single443` is a mode switch and still
requires `FRP_CONFIRM_MODE_SWITCH=yes` (or `SWITCH` on a TTY). A genuine
fresh install with no `config.json` does not require that confirmation.

Recommended sequence:

1. Upgrade client software to 2.1.0+ while the server is still Direct
   (`sudo frpctl update`). This does not re-enroll or change ports.
2. Schedule a window. Re-run the server installer with
   `FRP_DEPLOYMENT_MODE=single443` and `FRP_CONFIRM_MODE_SWITCH=yes`
   (or type `SWITCH` on a TTY).
3. On each client, Apply (or otherwise contact the allocator) so
   `frp_transport=wss` is stored and `frpc.toml` is regenerated.
4. Confirm `sudo frpctl status` / `sudo frpctl doctor` on server and client.

Rollback of a failed cutover restores the previous `frps.toml` when the
frontend config is invalid or `frp-frontend` fails to start, then restarts
frps. A completed cutover is reversed by reinstalling with
`FRP_DEPLOYMENT_MODE=direct` and `FRP_CONFIRM_MODE_SWITCH=yes`, then Apply
on clients so they return to `tcp`.

## Firewall notes

The installer does **not** change OCI Security Lists, AWS security groups,
UFW, firewalld, or host iptables.

Direct mode public inbound: **TCP/443**, **TCP/6099**, **TCP/6000-6098**.
Single-443 public inbound: **TCP/443**, **TCP/6000-6098** only. Do not publish
the allocator backend (default 6099) or the FRP control backend (default 7000).

Some OCI Ubuntu images ship iptables INPUT with SSH ACCEPT and a catch-all
REJECT that is **not** UFW. Opening the public ports above in the cloud
security list is not enough if that host filter remains. Do not flush OCI
metadata / link-local / block-volume rules. Add explicit ACCEPT rules for the
public ports this mode documents, or use the image’s supported firewall tool.

`frpctl doctor` classifies `TLS_RESET` when TCP works but TLS is reset, and
points at single-443 rather than HTTP downgrade.

## Configuration fields

Stored in `/etc/frp-auto-deploy/config.json`:

| Field | Direct | single-443 |
| --- | --- | --- |
| `deployment_mode` | `direct` | `single443` |
| `frp_transport` | `tcp` | `wss` |
| `listen_host` | `0.0.0.0` | `127.0.0.1` |
| `frp_control_bind_addr` | `0.0.0.0` | `127.0.0.1` |
| `frp_proxy_bind_addr` | `0.0.0.0` | `0.0.0.0` |
| `frp_control_public_port` | 443 default | same public port as allocator |
| `frp_control_listen_port` | usually 443 | default 7000 (localhost) |
| `allocator_public_port` | 6099 default | same as control public |
| `allocator_listen_port` | 6099 | 6099 on localhost |
| `allocator_public_url` | `https://host:6099/enroll` | `https://host/enroll` |

Environment: `FRP_DEPLOYMENT_MODE=direct|single443`,
`FRP_CONFIRM_MODE_SWITCH=yes` for a non-interactive mode switch.
Internal backend ports can be overridden with the existing
`FRP_CONTROL_LISTEN_PORT` and `FRP_ALLOCATOR_LISTEN_PORT` variables.
The WebSocket path is not an installer setting.
